# 시험 도구 자체에서 배운 것

시험이 틀리면 품질을 잘못 판단한다. 아래는 시험과 평가 도구에서 실제로 겪은 일이다.

## e2e 무작위 실패 (2026-11-03~04)

전체 e2e가 실행마다 다른 시험에서 시간 초과로 실패했다. 병합 기준을 채우지 못해 원인을 찾았다.

| 실행 | 결과 | 시간 | 조건 |
|------|------|------|------|
| `next dev`, 개발 서버 켬 | 108/112 | 15.4분 | 남은 RAM 약 0.4GB |
| `next dev`, 개발 서버 끔 | 111/112 | 17.9분 | 남은 RAM 약 0.34GB |
| `next dev`, 개발 서버 끔 | 111/112 | 11.0분 | 남은 RAM 약 0.41GB, 이번엔 다른 시험 |
| 운영 빌드 | **112/112** | **2.8분** | 남은 RAM 약 0.4GB |
| 운영 빌드, 시험 추가 후 | 117/117 + 성인 끔 1 | 2.6분 | |
| 운영 빌드, 깨끗한 클론 `ci:local` | 12/12 단계 | 웹 시험 161초 | |

**실패의 공통점:** 전부 "눌렀는데 15초 안에 반응이 없다"였다. `next dev`는 화면과 서버 액션을 처음 쓸 때 컴파일한다.

**판단 과정:**

1. 처음에는 메모리 부족으로 봤다. 개발 서버를 꺼도 메모리가 늘지 않았고 실패도 남아, 이것만으로는 설명되지 않았다.
2. 시간 제한을 늘리면 통과했겠지만 원인을 덮는 일이라 하지 않았다.
3. 컴파일을 없애면 모든 실패가 사라지는지 봤다. 같은 메모리에서 전부 통과했으므로 원인으로 판단했다.

운영 빌드는 운영과 같은 CSP와 쿠키로 돌아 더 실제에 가깝다는 이점도 있다. 대신 화면 코드를 고치면 빌드를 다시 해야 한다.

## 평가 도구의 결함 (2026-10-15)

이모지 정규식을 잘못 써서 이모지가 없는 답에도 "이모지 사용"이 붙었다. 18개가 전부 실패로 나와 이상하다고 보고 찾았다. **결과가 극단적이면 도구부터 의심한다.**

## 그림 평가에서 만든 사고 (2026-11-04)

정규 평가가 아니라 작업 중 일어난 일이다. 긴 명령에 넣은 `set -e`가 멈추지 않아, 충돌한 병합 위로 기록 커밋이 올라갔다. 그 뒤로 병합과 커밋을 한 명령으로 묶지 않는다.

## 부하 측정 (`npm run bench -- --users 8 --delay 1500`)

가짜 LLM을 1.5초·직렬로 돌려 로컬 Ollama 한 대를 흉내 낸다. 실제 모델 속도가 아니라 **대기열의 동작**을 본다.

| 시나리오 | 2026-10-15 | 2026-11-06 |
|----------|------------|------------|
| 읽기 8명 동시 | 927 req/s, p95 13ms | 2300.6 req/s, p95 5ms |
| 대화 8명 동시 p95 | | 12.0초 |
| 이어지는 대화 8명 × 9번 p95 | 12.0초 (대기열 넣기 전 33.0초) | 12.0초 |
| 마지막 답 뒤 이야기 정리 완료 | 평균 약 20초 지연 | p50 19.8초, p95 24.3초 |
| 오류 | | 0건 |

읽기 처리량이 늘어난 까닭은 재지 않았다. 측정 때 PC 상태가 달랐고, 이번에는 API가 같은 PC의 다른 무거운 프로세스와 경쟁하지 않았을 수 있다. 12.0초는 1.5초 × 8명이라 모델 직렬 처리의 이론값과 같다. 대기열이 기다리는 답을 먼저 처리한다는 뜻이다.

## 시드와 반복

판정과 요약은 시드를 고정한다. 그래서 같은 입력을 반복해도 독립 시행이 아니다. `--repeat`를 늘려도 판정 쪽 표본은 커지지 않는다. 장면을 늘려야 한다. 반면 시드가 없는 연기 쪽은 같은 코드로 4/8과 2/8이 나왔다. 8번으로 개선을 말하면 안 된다.
