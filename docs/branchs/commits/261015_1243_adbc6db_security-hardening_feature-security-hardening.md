## 주 내용

- `security/rate-limit.ts`: 요청 한도(429 + `Retry-After`) — 로그인·가입·비밀번호 변경·대화·대답 추천·공방 LLM 호출·기억 정리·업로드·신고·안내 도우미
- 실제 이용자 IP를 `X-Forwarded-For`로 넘기고 API는 루프백·사설 주소의 헤더만 신뢰(`trust proxy`)
- 보안 헤더(API·웹), `X-Powered-By` 제거
- 약한 비밀번호 거절 (흔한 값·같은 글자 반복·이메일 아이디와 같은 값)
- 이용약관·개인정보처리방침·고객센터·사업자 정보를 실제 동작에 맞춘 초안으로 (`legal-doc` 컴포넌트)
- 단위·통합 테스트 14개, e2e 5개, API 문서(한도 표)·`.env.example`

## 상세

**배경**
사용자 요청(보안·운영 최소선이 비어 있다는 약점 개선). 로그인 시도 제한, AI를 부르는 요청의 남용 방지, 보안 헤더, 약관·개인정보처리방침의 실제 내용이 없었다.

**변경 범위**
apps/api(security 신규, auth, character-chat, studio, memories, reports, agent-chat, main.ts), apps/web(약관 4페이지, legal-doc, client-ip, next.config), e2e, docs

**기술 포인트**
- 한도는 이름 붙은 규칙 표(`RULES`)와 `@RateLimit('chat')` 데코레이터로 라우트에 붙이고 전역 가드가 센다. 사람 기준은 토큰 서명만 확인해(DB 조회 없음) 센다. 로그인은 "같은 이메일을 같은 곳에서"와 "한 곳에서 이메일을 바꿔 가며"를 따로 막는다.
- 구현 중 설계 결함을 스스로 발견해 고쳤다: 웹 서버가 대신 API를 부르므로 API가 보는 IP는 늘 웹 서버 주소라, IP 기준 한도(로그인·가입·안내 도우미)가 모든 이용자를 한 사람으로 세어 40번째 로그인 시도부터 사이트 전체가 막힐 뻔했다. 실제 이용자 IP를 `X-Forwarded-For`로 넘기고, API는 루프백·사설 주소에서 온 헤더만 믿게 했다(공개 주소에서 헤더로 IP를 꾸미지 못함). 서로 다른 IP가 따로 세어지는 것을 통합 테스트로 고정했다.
- 운영에서는 웹 앞단(프록시)이 `X-Forwarded-For`를 덮어써야 이용자가 IP를 꾸며 한도를 피하지 못한다. 문서에 적었다.
- 카운터는 서버 메모리의 고정 창이다. 서버가 여러 대가 되면 공유 저장소가 필요하다(문서·코드 주석에 명시). `RATE_LIMIT=off`·`RATE_LIMIT_SCALE`로 조절할 수 있고, e2e는 한도를 1000배로 곱해 돌리며 한도 자체는 통합 테스트가 검증한다.
- 약관·처리방침은 서비스가 실제로 하는 일에 맞춰 썼다(수집 항목, 비밀은 AI에 보내지 않음, 쿠키 2종, IP를 저장하지 않음, 탈퇴 기능이 아직 없어 문의로 삭제 등). 법률 검토 전 초안이라는 사실을 문서 맨 위에 밝히고, 운영자가 채울 칸은 [대괄호]로 남겼다. 법적 효력이 있는 문서가 아니다.
- 엄격한 CSP(스크립트 출처 제한)는 Next의 인라인 스크립트와 맞춰야 해서 `frame-ancestors`만 넣었다.

**안 한 것**
이메일 인증·비밀번호 찾기(메일 발송 서비스가 필요), 이미지 내용 자동 검수(비전 모델 없음), 엄격한 CSP, 공유 저장소 기반 한도, 법률 검토
