## 주 내용

- `ai/ai-queue.ts`: AI 호출 대기열. 동시 호출 수 `AI_CONCURRENCY`(기본 2), 기다리는 답이 배경 작업보다 먼저
- `ai-client.ts`: 대기열 경유 + 타임아웃(기다리는 답 130초, 배경 150초 → 504), 대기 60초 초과 503
- 기억 정리·이야기 요약은 배경 작업으로 돌리고, 배경 대기열이 20개를 넘으면 건너뜀
- `GET /health`에 대기열 상태(`ai`) 노출
- 대화 목록·저장 목록의 항목별 쿼리(N+1)를 쿼리 한 번으로 묶음
- 가짜 LLM에 지연·직렬 처리 모사, `npm run bench` 부하 측정 도구 추가

## 상세

**배경**
사용자 요청("성능" 약점 개선). 모델 하나를 여러 사람이 나눠 쓰는데 호출을 제한하지 않아, 뒤에서 하는 정리 작업이 사용자가 기다리는 답을 밀어냈고 모델이 멎으면 요청이 영영 매달렸다.

**변경 범위**
apps/api(ai, memories, campaign-state, health, conversations), services/ai(fake_llm), e2e/bench.mjs, docs

**기술 포인트**
- 동시 호출을 제한하고 기다리는 답을 우선 처리한다. 배경 작업은 한 자리를 항상 기다리는 답에게 남겨 둔다.
- 대기열이 가득 차거나 오래 기다리면 계속 쌓지 않고 안내와 함께 거절한다(배경 작업은 다음 기회에 다시 시도).
- 목록의 마지막 대화는 `DISTINCT ON`으로 한 번에 가져온다.

**안 한 것**
프로세스가 여러 개일 때 대기열 공유(지금은 프로세스 하나당 하나), 응답 스트리밍

## 결과

**동작 확인**
- API 135개 통과(대기열 단위 테스트 포함), 타입 검사 통과
- e2e 31개 통과
- 부하 측정(8명, 모델 1.5초 직렬): 연속 채팅 p95 33.0초 → 12.0초, 읽기 927 req/s(p95 13ms), 이야기 정리는 약 20초 지연되나 완료

**리스크**
대기열이 프로세스 메모리라 서버를 여러 대로 늘리면 대수만큼 동시 호출이 늘어난다.

**후속**
배포 시 서버 구성에 맞춰 AI_CONCURRENCY 조정
